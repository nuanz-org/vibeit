# Taste
- Prefers brainstorming and discussion of ideas and architecture before any code is written; explicitly asks the assistant not to code during ideation and plan-review phases — has stopped the assistant mid-implementation ("no just review the plan", "dont code") when it began executing a plan they wanted reviewed further. Confidence: 0.95
- When asking to review or assess the codebase ("check the architecture"), expects the assistant to actually go through the code — reading/exploring the repository directly — rather than relying on memory or doc search. Confidence: 0.7
- Writes in very fast, heavily typo-laden shorthand ("shoesu" = should you, "resurl" = result, "abotu" = about); expects the assistant to decode the intended meaning and answer directly without asking for clarification. Confidence: 0.8
- Wants clear, opinionated prioritization when discussing improvements — asks "what should I change first" and expects a recommended sequence with reasoning, not just a flat list of options. Confidence: 0.7
- Brings fully-written implementation plans (phases, file-change maps, acceptance criteria) for review before executing and expects them vetted rigorously — verifying the plan's specific claims (file paths, exports, CSP strings, config) against the actual code and flagging concrete gaps, not a surface-level thumbs-up. Confidence: 0.75
- Iterates plans through an explicit review loop: after feedback, returns a revised plan with a "Revisions from review" table mapping each feedback item to its fix (observed across three successive revisions of the same plan). The loop ends one of two ways: (a) greenlights with a terse signal ("now") — expects immediate execution of the locked plan, not another review round; or (b) takes the plan to implement personally ("i will be implementing it") — in that mode the assistant's role stays strictly review-only: a final verification pass plus implementation pitfalls/gotchas, no code. Confidence: 0.85
